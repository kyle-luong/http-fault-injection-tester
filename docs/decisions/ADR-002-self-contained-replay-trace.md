# ADR-002: A replay trace is self-contained, and carries no payload

**Status:** accepted, M4 (owner-approved 2026-11-12)
**Affects:** the trace file format, which is a published wire format

## Context

`faulttest replay --trace PATH` takes one argument. For the command to mean
anything, the trace has to carry enough to rebuild the case: the fixture mode,
the retry policy, the invariant, the operation's numeric delta, and the fault
decisions that were injected.

That collides with a safety rule the PRD and `CLAUDE.md` both state outright:
*don't store private headers or request bodies in traces*. The scenario's
`delta` is a field of the request body. Taken literally, the rule forbids a
self-contained trace.

Two options:

1. **Embed the validated scenario.** Replay needs no other file. The trace then
   contains `delta`, which is request data in the narrow sense -- though it is
   the harness's own synthetic test configuration, not anything a caller sent.
2. **Reference the scenario by path and digest.** The trace stays free of
   anything body-shaped, but replay depends on a file it does not control, and a
   trace loses its meaning when that file moves or changes. The digest turns a
   moved file into an error rather than a wrong answer, which helps, but it does
   not make the trace self-contained.

## Decision

Option 1, bounded by the owner's clarification:

> For built-in synthetic test fixtures, traces may embed the minimal validated
> scenario configuration, including fixture type, retry policy, invariants, and
> synthetic numeric parameters such as delta. This is permitted as test
> configuration, not captured HTTP traffic.
>
> Do not serialize arbitrary request bodies, credentials, authentication
> headers, or sensitive user data. For future scenarios involving arbitrary
> payloads, use an external scenario reference with a verified digest instead.

So the embedded scenario is permitted *because* the payload is synthetic and
generated by the harness. For the request itself the trace stores only `method`,
`path` and `payload_digest` -- never the bytes and never a header. The digest is
computed by the same function that builds the body (`client.PayloadDigest` over
`client.operationBody`), so it cannot come to describe bytes the client no
longer sends.

The trace also records the per-case deadline. It is configuration, not
metadata: the same trace replayed under a different deadline can reach a
different verdict, so `replay` has no `--timeout` and takes it from the record.

One request-side value does appear. `expected.state.operations` holds the
operation identifiers the fixture applied, which are the harness's idempotency
keys **as the oracle read them back out of application state**, not as captured
from a request. Saying "a trace holds no header value" would be false, so
nothing here says it.

A digest over the embedded scenario (`scenario_digest`) binds it to the rest of
the file, so editing an invariant or a fixture mode and leaving the digest alone
is refused rather than replayed.

Replay injects the **recorded decisions**, not the scenario's matching rules.
Deriving them again from the embedded rules would mean both sides of the
comparison came from the same place, and a trace that no longer described its
run could not be detected.

## Consequences

- A trace is portable: an operator can attach one to a bug report and the
  recipient needs nothing else to reproduce the case.
- The schema is strictly parsed with unknown keys rejected, so every key written
  now is frozen for v1. A field that needs to change needs `schema_version` 2.
- The moment a scenario can carry an arbitrary payload, option 1 stops being
  available and the trace must switch to an external scenario reference with a
  verified digest. That is the owner's instruction, and it is a v2 change.
- Replay reproduces injected decisions and the oracle verdict. It does not
  reproduce goroutine scheduling, port allocation or timing, and a scenario
  whose verdict depends on a delay racing a client timeout can legitimately
  replay to a different verdict. The comparison names the axis that disagreed so
  the two cases stay distinguishable.
- A replay that does not reproduce its record exits 3, not 1: the tool failing
  to reproduce itself is infrastructure failure, and exit 1 keeps meaning that
  the oracle found a violation in the application under test.
- **The digests are not signatures.** They catch a partial edit, which is the
  realistic accident for a file that travels in bug reports; they cannot catch a
  trace rewritten wholesale with its digests recomputed. A trace is input,
  trusted as far as a scenario file is, and replay establishes that the embedded
  configuration reaches the recorded outcome -- not that the record is genuine.
  Signed traces would be a different decision, and are not needed for a local
  testing tool.
- Duplicate JSON keys are accepted with the last winning, as they are in
  scenario and result parsing, so a crafted file can read one way to a human and
  execute another. Detecting them needs a token walk; the exposure is recorded
  rather than fixed, and "strictly parsed" in these documents means unknown keys
  and trailing content, not duplicate keys.
- `scenario_digest` and `payload_digest` cover the Go encodings of the scenario
  and the request struct. The day either schema changes, stored traces are
  rejected with a message that says the file may have been written by a build
  whose schema differs -- correct, but it means a trace is only readable by
  builds that agree on those two shapes, and `trace.schema_version` cannot
  express that pairing on its own.
